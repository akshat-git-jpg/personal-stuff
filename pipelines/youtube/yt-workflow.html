The question

Scripted software tutorial videos. TTS voiceover, not live human voice. Team split: the tutorial maker knows the tool; the video editor is strong at editing but does not know the tool. Which of the three workflows (A, B, C) fits best?

Workflow A - Record screen free, editor syncs

Tutorial maker records raw section-wise clips with no attempt to match TTS timing. Editor syncs everything on the timeline.

Pros

  • Fastest recording. No TTS in the ears.
  • Section-wise files = small sync problems, not one big one.
  • Editor uses their strengths (cut, motion graphics, b-roll).
  • Re-shoots are cheap (one section, not the whole video).

Cons

  • Editor can only trim well - stretching short clips looks laggy.
  • Needs a rule: record slower than the VO, leave 1-2s pauses between actions.
  • Screen action can feel disconnected from the words if the recorder rushes.

Workflow B - Editor records the screen

Editor understands the script and records the screen themselves.

Pros

  • Total control over sync in one head.
  • No handoff friction between roles.

Cons

  • Editor does not know the tool. Wrong clicks, wrong menus, wrong outcomes.
  • Not viable for real software tutorials.

Workflow C - Record screen in sync with TTS

Tutorial maker records the screen with the TTS playing, matching action to voice.

Pros

  • Screen action lands on the right words.
  • Editor mostly polishes - almost no sync work.
  • Feels natural. Actions match the pace of the voice.

Cons

  • Hard for a human. Recorder either rushes clicks or waits awkwardly.
  • Any script rewrite = re-record that section from scratch.
  • Slower recording. High cognitive load.

The core tension

Recorder pain vs Editor pain. C moves the sync burden to the recorder (hard to do live). A moves it to the editor (fine when trimming, ugly when stretching).

Editors can cut, but they cannot magic more screen time out of thin air. Slow-motion on a cursor looks wrong. Freeze frames look worse. B-roll cover-ups only work when there is a pause to drop them into. So Workflow A only works if the raw recording is always longer than the VO section - which means the recorder needs a discipline: click slow, leave pauses.

My recommendation: Workflow A

Pick Workflow A with one rule for the tutorial maker: "Click slow. Leave 1-2 seconds between actions. When in doubt, add another beat."

Why

  • Plays to team strengths: tutorial maker demos the tool; editor handles sync.
  • The "record slow with pauses" rule makes the editor's job easy: always cut, never stretch.
  • Section-wise recording keeps sync problems small and local.
  • C fights human nature. Nobody clicks in rhythm to a robot voice for 8+ minutes.
  • Matches how team-based YT tutorial channels operate: creator captures, editor assembles.

What the YouTube norm looks like

  • Solo YouTubers (Fireship, MKBHD) record their own voice while clicking - natural rhythm, no TTS. That is closer to C but only works with live voice.
  • Team-based scripted channels split it: recorder captures raw, editor assembles. That is Workflow A.
  • TTS-only channels follow the team pattern because TTS gives no natural rhythm to record along with.

Rule of thumb (the "how" for Workflow A)

  • Recorder: read the script aloud once for pace, then record slower. Pause between clicks. Do not chase the TTS.
  • Processor: deliver TTS with per-section timestamps so the editor knows how long each section should be.
  • Editor: trim the raw clip to the VO length. Fill any pause with a zoom, a motion graphic, or a b-roll. Never slow-motion the cursor.

Second opinion (independent Opus agent): pick Workflow C

A fresh Opus agent was asked the same question with no anchoring. It came back with the opposite call. The core points:

Kill Workflow B outright

Editor does not know the software. Making them record wastes the only expertise asymmetry that matters.

Why C beats A (the point I underweighted)

  • The person who knows the tool should make the timing decisions. In A, the editor decides pacing but does not know which click is the load-bearing beat vs a throwaway. They cut the wrong frame, hold on the wrong panel, miss the moment the viewer needs to see.
  • A hides a brutal review-and-redo loop. The tutorial maker keeps sending the cut back for pacing fixes. That is where A quietly bleeds hours.
  • TTS in headphones self-enforces the "record longer than VO" rule. In A, that rule is a hope. In C, the recorder literally cannot record too short unless they willfully rush - the VO is playing, they just wait for it to finish before clicking. Awkward waiting is the SAFE failure mode; that dead air is exactly what the editor trims cleanly.
  • TTS is deterministic. Section length is known before recording. Rewrites regenerate cleanly. TTS was made for C.

YouTube norm (Opus take)

  • Scripted tutorial/review content on YT is voice-first. MKBHD, LTT, most tech reviewers: script -> VO -> visuals cut to VO.
  • Solo YouTubers often go screen-first-then-narrate. Team channels almost always go voice-first because voice-first parallelizes cleanly across roles.
  • Faceless AI-voice channels: the ones that look good pre-sync the screen to the TTS. The ones that do not have that telltale "cursor drifting, VO over/under" feel that reads as low effort.

Opus rules for Workflow C

  1. Section by section, not one continuous take. One script beat = one clip.
  2. TTS in headphones, on loop, while recording that section.
  3. Recorder rule: when in doubt, wait longer. Never rush.
  4. Editor rule: no slow-motion on real footage, ever. Trim, speed-ramp, hold on stills, zooms/highlights over dead time.
  5. Script writer must know approx action time per beat before finalising. If the VO says "click Save" but the action is a 4-step wizard, the VO for that beat needs to be long enough.

Opus's fallback to A

Only if the recorder freezes up against a click track after an honest try. Then A survives only with a strict rule: every beat recorded at 0.7x the pace that feels natural, so the editor always has room to trim.

Final call (honest)

Two takes on the table. Sonnet says A. Opus says C. Opus's "editor does not know what matters" point is real and shifts the balance toward C. But your original worry (recording to TTS is hard) is also real.

How to decide

  • Try C first on one video. One section at a time, TTS in headphones. If the tutorial maker can hold pace without freezing, you win: sync is nearly free.
  • If C feels stiff after a real try, fall back to A with the "record at 0.7x pace" rule so the editor only ever trims.
  • Do not do B. Both agents agree on this.
