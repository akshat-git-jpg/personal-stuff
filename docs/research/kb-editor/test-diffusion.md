# Diffusion Studio editor: hands-on test (2026-10-17)

Candidate: `diffusionstudio/editor` v0.214.0 (MPL-2.0), commit `1ac2f5cc` (2026-10-16). Tester ran on the owner's Apple Silicon Mac.
Work folder: `/Users/kbtg/.claude-work/jobs/2b878578/tmp/candidates/diffusion/`.
Protocol: TEST-PROTOCOL.md, with the coordinator's fast-track changes: T9 and T10 answered from the code only, T4 with 5 seeks, T6 on a 2-minute dense segment, T8 time-boxed to 30 minutes.

## Setup facts (measured)

- **Release binary:** `Diffusion-Studio-arm64.dmg` from GitHub release v0.214.0. Its sha256 `6aa71613…4b07` matches the release asset digest. It is signed `Developer ID Application: Konstantin Paulus (BYVQNNK2TH)`. I copied the .app out of the DMG and removed quarantine on that copy only. The app ran with `HOME` and `--user-data-dir` pointed into the work folder, so it could not touch `~/.claude.json` or the real profile.
- **The release binary puts the whole editor behind a sign-in wall.** `AuthGate` in `apps/web/src/app.tsx` wraps the dashboard and project routes. With no Supabase session it shows only "Sign in or sign up" (Google, GitHub or magic link). I did not sign in.
  - Without login, the MCP server at `127.0.0.1:3274/mcp` still answers. These tools work: `probe`, `grab`, `context` and `open`. `open` even writes the project files.
  - These tools fail with "No project open": `capture`, `check` and `export`. The editor never mounts the project behind the login page.
  - So **T1-T7 and T11 could not run on the release binary without an account.**
- **Workaround: my own build from source with 3 small patches**, which is what a fork would do:
  1. Remove the login gate (`app.tsx`, -6 lines).
  2. Turn analytics off by default (`desktop/src/analytics.ts`, renderer `lib/analytics.ts`).
  3. Turn off the auto-updater (`desktop/src/main.ts`).

  `npm ci` took 24 s and `npm run package` took 45 s. All T1-T7, T8 and T11 numbers below come from this build (`apps/desktop/out/Diffusion Studio-darwin-arm64`).
- **Telemetry (from the code):**
  - The packaged app always sends usage events to `api.diffusion.studio/api/v2/trpc/events.track`: install, open, app_used every 60 s, canvas edit counts, code-change counts. It sends them even when signed out (no bearer token).
  - There is **no opt-out setting**. The only switch is `DIFFUSION_ANALYTICS`, and it can only turn analytics *on* in dev builds.
  - The auto-updater polls `update.electronjs.org` (seen in the release log: `checking-for-update`, `update-not-available`).
  - The app also loads a local SAM-2 ONNX model at startup (onnxruntime warnings in the logs).
- **MCP registration:** the app writes its entry into `~/.claude.json` (and Cursor, Codex and other agents' configs) only when the user clicks "Install agent tools" in Settings. `healMcpRegistrations()` runs on every launch, but it only rewrites an entry that already exists. I did not click it. All MCP calls in this test came from `harness/mcp.mjs`, a 30-line Streamable-HTTP client.
- **Parallel run:** WeftCut was running the whole time (pid 48894, later 18843). It held `perf.lock` from before my first try until 19:28:43, when this tester took it. It was released at 19:56. During T3/T4/T6 the WeftCut app was still open but mostly idle (0.5-5% CPU; one 106% sample at lock time). An unrelated `ffmpeg` (about 50% CPU, parent unknown) and VS Code were also busy, so treat the perf numbers as slightly pessimistic. Every non-perf number below (T1, T5 captures, T7, T11) was measured while WeftCut was running.

## Surprises

- The release app is useless signed-out (only probe and grab work). The open-source code is not: 3 tiny patches give a full local editor with no account.
- The HyperFrames cards worked with a generic adapter and no card edits. 15/20 render as live DOM composited on the canvas, with real alpha.
- Agent edits clear the undo history. That is a design choice (the source file is the document), and it clashes with "Claude edits, the human tweaks, the human hits undo".
- Telemetry cannot be switched off in the shipped binary.
- Release cadence: 10 releases in 23 days (v0.206-0.214). The API surface moves fast.

## Measured vs inferred

Measured: everything with a number, plus the screenshots and SSIM values. Inferred: the cause of the 5 blank cards, T9 and T10 (code reading only), Windows behaviour (not tested; Windows code paths exist: `cli-windows.ts`, `cloud-sync-windows.ts`, squirrel installer).

## Verdict

**Not a good base to fork and own for years, as things stand.**

What is right:
- The architecture matches requirements 1, 3 and 8 well. The project is code, the agent edits it, and edits show live in about 0.5 s. A rich MCP/CLI covers inspection. Live HTML layers run in the editor, and 15/20 HyperFrames cards work through a generic adapter.
- The code is clean and documented. A real feature took about 6 minutes plus a 39 s rebuild.
- Licence is MPL-2.0.

What sinks it on this kit:
1. **Export failed in every attempt, even without HTML.** Live preview **loses the 4K VFR screen recording** past about 5 minutes. Those recordings are the owner's core media, so requirement 5 (WYSIWYG, export once) is not met.
2. **HTML-in-Canvas is an origin-trial API with documented rasterizer bugs.** 5/20 cards are blank, and their layers escape the canvas in the live view. A fork inherits a Chromium dependency it cannot fix.
3. **The product is wired to the vendor's cloud.** There is a login wall, telemetry with no opt-out, an auto-updater and cloud transcription. A fork has to strip these and keep stripping them at 10 releases in 23 days, with a bus factor of 1 (809 of 813 commits by one author).
4. **Agent edits wipe the undo history by design.** That clashes with the "Claude edits, the human tweaks" loop.

If it is revisited, retest export with a CFR transcode of the recording (not done here; the brief rules out pre-conversion), and check whether a newer release fixes VFR decoding.
